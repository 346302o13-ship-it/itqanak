# فحص الملفات

يوحد `@itqanak/storage` الفحص خلف `MalwareScanner`. لا تقرأ الخدمات
`FILE_SCAN_MODE` مباشرة ولا تفسر تعطيل المحرك كنجاح فحص.

## أوضاع التشغيل

القيم الوحيدة المقبولة:

```text
FILE_SCAN_MODE=disabled
FILE_SCAN_MODE=clamav
```

- التطوير والاختبارات العادية افتراضيًا `disabled`. يعيد adapter
  `SKIPPED_DEVELOPMENT` ويدمر stream؛ لا يعيد `CLEAN`.
- ClamAV ضمن profile اسمه `antivirus` في Compose التطويري والإنتاجي، ولا يبدأ مع
  `docker compose up` العادي.
- يبقى `FILE_SCAN_MODE=clamav` في Web وWorker الإنتاجيين باعتباره **قدرة جاهزة** كي
  يستطيع المدير تشغيل الفحص بلا إعادة نشر. مصدر قرار التشغيل هو
  `platform_operational_settings.file_scan_queue_paused`، وقيمته الافتراضية `true`.

لتجربة المكدس مع المحرك محليًا، عيّن `FILE_SCAN_MODE=clamav` في `.env` ثم شغّل:

```bash
docker compose --profile antivirus up --build -d
```

إعادة تشغيل ClamAV وحده لا تغير وضع Web أو Worker؛ الإعداد المركزي هو مصدر السلوك.

## ClamAV TCP

يستخدم adapter بروتوكول TCP `INSTREAM`، ويرسل chunks لا تتجاوز 64 KiB، وينهي الإطار
بصفر. يقيد مهلة الاتصال ومدة الفحص وحجم الاستجابة، ويحول الرد إلى `CLEAN` أو `INFECTED`
أو `ERROR` دون إعادة signature أو عنوان المحرك للعميل. يستخدم readiness أمر `PING` فقط.

الإعدادات الافتراضية:

```text
CLAMAV_HOST=clamav
CLAMAV_PORT=3310
CLAMAV_CONNECT_TIMEOUT_MS=3000
CLAMAV_SCAN_TIMEOUT_MS=30000
FILE_SCAN_MAX_ATTEMPTS=5
```

لا تعرض health responses المضيف أو المنفذ أو نص خطأ ClamAV.

## دورة العامل

عند رفع ملف جديد بينما القرار التشغيلي مفعّل يكتب التطبيق حدث الفحص المناسب في
`outbox_events`. أما الرفع أثناء الإيقاف فيثبت `SCAN_SKIPPED_BY_ADMIN` ولا يكتب مهمة
فحص، ولذلك لا يؤدي التشغيل اللاحق إلى فحص الملفات القديمة تلقائيًا. لا يطالب العامل
بأي مهمة حتى تكون الرغبة مفعلة ويسجل مشغل المضيف `RUNNING` بعد نجاح Docker health؛
لذلك لا تُستهلك محاولات إعادة الفحص أثناء إقلاع الحاوية. بعد ذلك:

1. يطالب دفعة bounded باستخدام `FOR UPDATE SKIP LOCKED` وlease قابلة لاسترداد العمل
   المتوقف.
2. يقفل outbox ثم attachment وفق ترتيب ثابت، ويستخدم attempt count كـfencing token حتى
   لا تكتب نتيجة scanner قديمة فوق محاولة أحدث.
3. يفتح الجسم الخاص كبث ويرسله إلى المحرك.
4. يثبت `CLEAN` ويجعل الملف قابلًا للتنزيل، أو يثبت `INFECTED` وينقله ذريًا إلى
   `DELETE_PENDING` ثم يحذف الجسم ويثبت `DELETED`.
5. عند خطأ مؤقت يعيد job إلى `RETRY` بتأخير أسي محدود مع jitter. بعد الحد الأقصى يثبت
   `SCAN_ERROR` ويضع outbox في `DEAD_LETTER`؛ يبقى الملف غير قابل للتنزيل.
6. يرفع نسخة الطلب ويسجل `FILE_SCAN_COMPLETED` أو `FILE_SCAN_FAILED` في سجل الطلب.

إذا فشل حذف جسم مصاب، يبقى `DELETE_PENDING` وتكمله مصالحة التخزين. حذف جسم مفقود
مسبقًا يعد نهاية idempotent، أما 403 أو خطأ شبكة فلا يعامل كأنه مفقود.

يمكن تشغيل دفعة يدويًا:

```bash
pnpm files:scan-pending
```

الأمر يحتاج إعداد التخزين والفحص الفعليين. العامل يشغل الدفعات تلقائيًا في التشغيل
العادي. هذه دفعة تغيّر حالات الفحص وليست أداة معاينة؛ لا يوجد لها dry-run، وتمرير
`--dry-run` مرفوض قبل فتح اتصال قاعدة البيانات. استخدمها دون هذا العلم فقط عندما تقصد
معالجة دفعة فعلية.

يمكن للمدير تشغيل الفحص أو إيقافه من صفحة التشغيل والصيانة. عند الإيقاف، يعلق Worker
المطالبة بمهام قائمة ويوقف مشغل systemd المعزول الحاوية لتحرير الذاكرة. الملفات الجديدة
تُخزّن خاصة بحالة `SCAN_SKIPPED_BY_ADMIN` وتُرسل مع التحذير وسياسة التنزيل المقيدة؛ لا
تُعتبر نظيفة. عند التشغيل يبدأ ClamAV وتدخل **الملفات الجديدة فقط** `PENDING_SCAN`.
إعادة فحص ملفات skipped تتطلب إجراءً إداريًا منفصلًا مقصودًا وغير متاح تلقائيًا.
التفاصيل الأمنية وخطوات التحقق في
[`OPERATIONAL_CONTROLS.md`](./OPERATIONAL_CONTROLS.md).

## Readiness

تعرض `/api/health/ready` إحدى القيم الآمنة فقط:

| القيمة                 | الأثر                                            |
| ---------------------- | ------------------------------------------------ |
| `disabled-development` | ناجح في بيئة التطوير؛ لم يجر فحص ملفات.          |
| `disabled-by-admin`    | الفحص غير مطلوب؛ لم يؤكد مشغل المضيف التوقف بعد. |
| `healthy`              | ClamAV يجيب `PONG`.                              |
| `paused-stopped`       | توقف مقصود أكده مشغل المضيف؛ readiness ناجحة.    |
| `unavailable`          | readiness تفشل وتعيد 503.                        |

يفحص heartbeat العامل ClamAV عندما يكون الوضع `clamav` والفحص مطلوبًا. أثناء توقف
مقصود يستمر heartbeat وبقية عمل العامل دون الفحص. لا يحتاج migrator أو أدوات المصادقة
إعداد S3/ClamAV لأن متطلبات config محددة لكل process.

## الاختبار والتعامل مع الملفات غير المفحوصة

اختبارات TCP الوهمية تغطي النظيف والمصاب والخطأ. اختبار ClamAV الفعلي opt-in ويعمل فقط
عند ضبط `TEST_CLAMAV_HOST`، وينشئ EICAR القياسي وقت الاختبار من أجزاء بدل حفظ عينة في
Git. لا تنقل كائنًا ذا `SCAN_SKIPPED_DEVELOPMENT` إلى بيانات الإنتاج على أنه آمن؛ أعد
رفعه أو افحصه في بيئة موثوقة ثم سجل provenance صحيحًا. لا تغيّر
`SCAN_SKIPPED_BY_ADMIN` يدويًا إلى `CLEAN`؛ النتيجة النظيفة لا تنتج إلا من processor.
